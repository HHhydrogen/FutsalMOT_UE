# 单仓库结构评估（2026-10-25）

状态：本文保留最初评估依据；随后用户明确要求开始融合，执行记录见 [单仓库迁移](SINGLE_REPOSITORY_MIGRATION_20261025.md)。当前训练与追踪继续使用原目录和原冻结源码。

## 结论

建议本项目后续使用一个 Git 仓库，以现有 `FutsalMOT_UE` 为主仓库，直接管理 `Content/FutsalMOT/code/`。UE 采样、Python 导出和研究实验紧密耦合，同一次功能变更经常跨两边；统一提交可以避免子仓库提交、推送和外层指针更新的三段操作。代码路径保持原样，环境隔离仍保留。

代价是 Python 代码不再有独立的发布边界，单独获取 Python 项目也会变得不方便。如果未来需要单独发布生成器，可从统一历史中导出，不必现在为此维持两套日常提交流程。UE 二进制资产仍使主仓库较大，合并仓库本身不会减少资产体积或替代 Git LFS 策略。

## 已核对的现状

- 外层 `master`：69 个可达提交，HEAD `383a27ebe04396e422cb31f1c0e79b151741b023`。
- 内层 `main`：148 个可达提交，HEAD `861d83082b65a2e7a3f26b60c41ce715b8793037`，452 个已跟踪文件。
- 外层以 mode `160000` 记录同一个内层 HEAD，`.gitmodules` 指向 `HHhydrogen/FutsalMOT_Dataset`。
- 内层 `.git` 当前是独立目录。不能直接删除它来代替历史迁移。
- 两边都有未提交或未跟踪内容，其中包括当前 v4 功能和未完成号码系统。未完成号码代码、资产和其他工作必须保留，但不能混入阶段成果提交。
- `Saved`、研究结果、数据集、虚拟环境和缓存继续排除在版本控制之外。统一 Git 不改变这些边界，也不能保护尚未保存的 Editor 内存。

## 执行顺序

1. 等当前六臂训练、六臂真实追踪及相应驱动完整结束；先完成 Saved/Research 恢复 D 盘。此时再执行仓库转换，避免改变正在运行的代码或路径。
2. 分别保存两仓库的完整 refs/历史 bundle，验证 bundle 可读取；另外保留二进制 diff、暂存区状态、未跟踪文件和需保留的忽略文件。`git bundle` 不包含未提交工作，不能把 bundle 当作完整工作区备份。
3. 在隔离的临时克隆中演练完整历史导入，将内层已提交树放入 `Content/FutsalMOT/code/`，保留两个提交图；不重写已发布外层历史，不使用 squash 丢弃内层历史，不 force-push。
4. 核对导入后的 452 个已跟踪文件及 mode 与原内层 HEAD 一致。旧内层提交仍可查询；其历史路径位于旧提交根目录，不能承诺普通路径 `--follow` 自动跨过前缀迁移。
5. 在备份和演练成功后，移除当前子模块 gitlink/配置和嵌套 Git 边界，恢复未提交工作，逐文件比对，改由外层跟踪实际代码。不能使用 `git add -A` 把号码和其他 WIP 一并纳入。
6. 更新 README、AGENTS 和提交说明；核对克隆后无需 submodule 初始化，两个 Python 环境和 UE 入口路径未变。精确暂存经过验收的迁移变更，正常推送到外层远端。
7. 原 `FutsalMOT_Dataset` GitHub 仓库保留为历史来源；是否归档属于独立远端管理动作，当前不删除或改其状态。

以上为最初建议顺序。用户后续明确要求开始融合，已先完成历史备份及真实Git夹具；实际采用不改工作区源码的索引导入，因而不必等待数据目录迁移。实际状态以迁移记录为准，未重写历史或归档旧远端。

## 依据

Git 官方介绍了将另一个项目导入子目录并保留历史的 [subtree 合并](https://git-scm.com/book/en/v2/Git-Tools-Advanced-Merging)。[git bundle](https://git-scm.com/docs/git-bundle) 用于保存和传输 Git 对象及 refs；未提交工作需要另外保存。[submodule 文档](https://git-scm.com/docs/git-submodule) 说明其独立仓库和上层引用关系。
